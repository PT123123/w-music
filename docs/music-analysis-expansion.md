# 音乐分析能力扩展：代码增量与接入方案

日期：2026-10-09。用途：供开发者据此拆任务、扩展 Python 分析引擎，以及接入 w-music 的分析界面与推荐功能。

本文基于当前两个仓库的源码阅读，不代表所有路径已通过音频实测。已有调用链见 [structure-analysis.md](structure-analysis.md)。本文中的新模块、函数名、字段名均为建议，不应误认为已实现。

## 1. 当前基础：哪些能力已经有了

### w-music：实时可视化和分析结果展示

- `core/src/Fft.cpp`、`core/src/SpectrumAnalyzer.cpp`：FFT、频段映射、增益与攻放平滑。
- `src/w-music/Audio/WasapiLoopback.cpp`：从默认输出端点采集系统混音。
- `src/w-music/Services/RecommendService.h/.cpp`：单曲/曲库分析请求、时间轴解析、结果缓存。
- `src/w-music/Views/NowPlayingPage.cpp/.h/.xaml`：结构卡、分析卡、事件展示与点击跳转。
- `src/w-music/Controls/StructureTimelineView.h/.cpp`：段落背景与单条动态曲线。

当前 `TrackTimeline` 保存一条响度绘制曲线、段落分组和动态事件。`ParseTimeline()` 主要解析 `dynamics.time_seconds`、`rms_norm`、元数据与事件；Python 返回的其他动态曲线没有作为可切换的独立曲线完整接入此数据模型和绘制控件。

### music-recommend：离线全曲分析已经更新

引擎根目录默认是 `C:/Users/ted/Desktop/music-recommend`，但实际位置应以 `RecommendService::RepoDir()` 解析结果为准。以下路径均相对于该引擎根目录。

- `features/extract.py`：已分开完整歌曲与最响窗口两种分析范围。
- `features/dynamics.py`：已输出全曲 RMS dBFS、相对响度、onset 活动、低频比例、频谱亮度、谱变化及 build/peak/pull-back/drop/release 事件。
- `features/structure.py`：已有候选边界、A/B/C 分组、段落时长比例、启发式功能标签与分数。
- `features/harmony.py`：已把旧版只有两种不同模板的问题修正为按根音平移的大小三和弦模板。
- `database/repository.py`、`api/server.py`：已有结构 JSON、分析版本、过期判断与读取接口。
- `recommendation/space.py`：结构相似度已使用能量曲线、重复分组等信息；不再把旧的主歌/副歌字符串序列作为唯一结构依据。
- `configs/config.yaml`：阅读时 `analysis.version` 为 3；实现新版本前需要再次确认，不能直接写死下一个版本号。

**本轮应在这些基础上增量扩展。不要重复提出“先实现全曲曲线、修复旧模板”作为新任务。**

## 2. 分析目标：先描述声音，不依赖曲风或真实乐器

需求来自用户对歌曲听感的比较与 AI 创作提示词。不能把所有流行歌都写成“主歌克制、副歌有力量”，也不能把“饱满、开阔、强、高潮”当作同一个指标。

建议把结果拆为以下维度。它们的定义可区分，但统计上可能相关，不能承诺完全独立。

1. **结构与重复**：段落边界、顺序、重复关系、片段长度。A/B/C 不是主歌/副歌的同义词。
2. **节奏与律动**：速度、拍点、起音次数、节拍内分布。重拍冲击强不等于 BPM 高。
3. **旋律与和声**：主旋律音高走向、音程、长音、和弦变化。音高高不等于响度大。
4. **音色与声音纹理**：明暗、噪声倾向、频谱分布、瞬态与持续性。适用于合成音、人声切片和无法命名的音源。
5. **空间属性**：左右差异、声像位置、混响/距离的估计。频谱宽不等于立体声宽。
6. **人声表现**：有无人声、音域、发音节奏、持续音、重唱/和声的候选线索。人声占比代理量不等于分离后的真实占比。
7. **随时间的变化**：以上维度在哪里、怎样变化。这才是动态走向的依据。

曲风标签作为补充：文件标签、平台分类、模型预测要注明来源。不要用“摇滚”推断一定有吉他，或用“民谣”推断动态平稳。

## 3. 优先增量一：把已有多条曲线真正接到播放器

### 为什么先做

引擎已有几条全曲曲线，但播放器主要显示相对响度。首先展示已有数据，比立即安装多个大模型更容易产生可检查的收益。

### Python 侧的字段核对与改进

修改 `features/dynamics.py`，保留旧字段并增加明确的字段语义：

- `rms_db`：短时电平，dBFS；不是感知响度 LUFS，也不是声压级。
- `onset_activity`：起音包络强度的代理量，无标准物理单位。
- `onset_rate_hz`：实际检测到的起音事件数 / 桶的真实时长，单位次/秒；这是新增功能。
- `low_band_ratio`：低频功率占总功率的比例；保留既有 `low_band_energy` 作兼容别名。
- `spectral_flux`：当前 `arrangement_change` 的具体算法名称；它是谱流，不是乐器数量或编曲层数。
- `spectral_brightness`：当前实现使用功率加权频率质心，Hz；注明加权方式，不能和其他模块的幅度加权质心不加说明地混用。

当前 `track_dynamics()` 中名为 `onset_density` 的曲线是 onset 包络的积分代理量，不是实际的起音次数/秒。不要仅改 UI 文案就把旧数据解释成次数。补算事件列表后才能输出 `onset_rate_hz`；旧字段保留并明确标注 deprecated / activity_proxy。

另外，核对 onset-strength 的输入约定。当前 `frame_curves()` 把线性幅度谱直接作为 `S` 传入；应按所用 librosa 版本的文档确定其尺度，选择约定一致的对数频谱或直接传音频，并重新标定阈值。避免数值看似可用，却在不同模块间含义不一致。

### w-music 侧增加哪些代码

在 `RecommendService.h` 中建议增加通用曲线结构，而不是给每种曲线复制一组硬编码成员：

```cpp
// 建议接口，尚未实现；具体 nullable 类型遵循项目习惯。
struct AnalysisCurve {
    std::wstring id;
    std::wstring unit;
    std::wstring meaning;
    std::vector<double> times;
    std::vector<double> values;
    std::vector<bool> valid;
    std::wstring scope;
};
// TrackTimeline 增加 curves；保留旧 curve/curveTimes，支持旧服务回答。
```

在 `ParseTimeline()` 中解析可用曲线，验证数组长度、有限数值、时间顺序和范围。字段缺失代表未计算；不能默认成零，零有可能是真实测量结果。每条曲线带独立单位和有效掩码，不能画成同一个无单位的 0–1 数字。

扩展 `StructureTimelineView`，允许选择“电平 / 起音活动 / 低频比例 / 明亮度 / 谱变化”。一轮先实现切换单条曲线；后续才增加多条叠加，并保证图例、归一化方式和读数含义清楚。

`NowPlayingPage` 保持同一套点击时间轴跳转行为，选点时展示该时间的实际值、单位和变化方向。

可描述：“这一段声音变亮，但电平近似不变”“低频比例下降，节奏活动上升”。不要直接输出“更有力量”。

## 4. 优先增量二：动态事件从单条电平驱动升级为多维变化

### 当前限制

`dynamics.events()` 主要从平滑后的 RMS 曲线找峰值和涨落，再用其他曲线支持评分。如果电平范围太小，函数会提前返回无事件。这会漏掉母带压缩较重、响度近似稳定但配器/律动变化显著的歌曲。

### 建议增加的代码

新增 `features/transitions.py`，或在 `dynamics.py` 中拆出独立的检测器：

```python
detect_axis_changes(curves, segments, config) -> list[dict]
merge_transition_evidence(axis_events, config) -> list[dict]
```

每个维度分别检测稳定、缓慢上升、缓慢下降、突然变化。电平曲线平稳时，只跳过该维度，不应跳过其他维度。

建议事件包含：`start`、`end`、`type`、`axes`、`evidence`、`score`、`score_kind`。例如 axes 指向低频比例、谱亮度、立体声差异，evidence 记录前后窗口均值、变化幅度、检测阈值和实际范围。

- “渐强”：明确是电平上升。
- “节奏活动增加”：起音数或包络活动上升。
- “音色变亮”：同一分析方式下的质心/高频比例上升。
- “声像扩展候选”：立体声差异指标增加；需要新增空间分析支持。
- “骤收”：一个或多个维度突然下降，并注明哪些维度。
- “综合高点候选”：多个维度共同支持；不要无条件显示为情绪高潮。

慢变化应结合秒级和段落级窗口；急停检测需使用短窗口。单一四秒平滑曲线不能同时准确定位微小瞬态、骤停和长时间铺垫。保留多尺度结果。

## 5. 优先增量三：用可组合的轮廓描述整曲

新增 `features/dynamic_profiles.py`：

```python
summarize_dynamic_profiles(curves, segments, events, config) -> dict
```

前面讨论的“8–12 种”是便于交流的自定义轮廓，不是公认的分类全集，也没有依据宣称覆盖所有歌单的 80% 或 90%。下面 12 项必须作为多标签属性组合，不能作为互斥曲风类别。

1. 全曲平稳：指定维度的段落差异低。
2. 交替对比：相邻两类段落反复出现明显落差；未确认主副歌时叫 A/B 对比。
3. 逐段增加：段落级趋势持续上升。
4. 逐段减少：段落级趋势持续下降。
5. 重复段落加码：同一重复组后几次的指定维度更高。
6. 开场即强：开头有效音乐部分已接近全曲该维度的高位。
7. 抽空再恢复：中间段下降后重新回到此前水平。
8. 单次突出高点：一个独立、显著的高位区间。
9. 多次突出高点：多个显著高位区间。
10. 高点后回落：主要高位区间之后存在持续下降。
11. 结尾骤停：音乐活动在较短时间内停止；需要排除文件截断、解码错误和末尾静音。
12. 尾段延展/渐弱：结束前有持续音乐，或指定维度缓慢下降。延展与渐弱分别记录子类型。

每项结果必须包含：指标维度、适用区间、分数、证据。不应凭“电平平稳”宣称整首歌所有维度都平稳，也不能把声场宽度提高叫成响度渐强。

例如展示：“A/B 交替对比（电平） + B 组第三次出现低频增强 + 中段起音活动骤降后恢复 + 尾段电平渐弱”。这比给四首不同歌都写“先抑后扬”更有辨识度。

## 6. 新增声音纹理分析：兼容电子音色与未知声源

新增 `features/texture.py`，复用整曲 STFT / 幅度谱 / 功率谱，避免每项功能重新计算 FFT：

```python
texture_curves(shared_spectral_frames, config) -> dict
summarize_texture_by_segment(curves, segments, config) -> list[dict]
```

可增加：

- 频谱平坦度：描述更接近音调性还是噪声性的频谱；高值不等于“使用了白噪声合成器”。
- 频谱带宽：频率分布的离散程度，Hz；必须注明幅度/功率权重，与立体声宽度分开。
- 高频功率比例、分频段谱变化：区分亮度上升发生在哪个频带。
- 峰值系数、起音峰密度、持续活动比例：为“短促/持续”提供候选线索。
- 谐波/打击性比例：如使用 HPSS，应注明代理性质及计算范围。

边界：混合音频里起音变密，可能来自人声、鼓、拨弦或合成音；持续声部也可能来自混响。不能根据几条曲线就断言发生了颗粒合成、time-stretch 或切片采样。

第一版报告“碎片状活动减少、持续成分增加”“噪声倾向和高频占比上升”。要确认“人声切片逐渐拉成长音”等具体音源过程，需要声源模型、分离信号或制作轨道，属于后续高成本能力。

## 7. 新增立体声分析：回答‘左右更宽’

### 首先解决输入信息丢失

当前 `music-recommend/preprocess/audio.py` 使用 FFmpeg `-ac 1`，并有单声道加载的回退路径；`features/extract.py` 也使用 `mono=True`。在此之后再做左右空间分析，无法还原立体声信息。

建议在预处理层保留可选的原声道分支：原始文件 → 立体声分析输入；同时继续生成旧的 mono 分支供现有算法使用。可以直接解码原文件或保存立体声中间文件，避免先转 mono 再伪造两个相同声道。传递原始声道数、实际采样率与分析源路径。多声道文件必须明确下混策略；不能随意把前两声道当成完整立体声混音。

### 新增模块与计算

新增 `features/spatial.py`：

```python
spatial_curves(stereo_audio, sample_rate, config) -> dict
```

可实现短时 L/R RMS、左右电平差、去均值后的左右相关度，以及 M/S 能量比例：`M=(L+R)/2`、`S=(L-R)/2`。按固定时间桶和分频段输出。

以下只是可测代理量：

- `lr_balance_db`：左右电平差。
- `lr_correlation`：左右相关度，范围 -1～1。
- `side_energy_ratio`：`E(S)/(E(M)+E(S))`，有效范围内 0～1。
- `mid_energy`、`side_energy`：注明信号归一化与量纲。

单声道文件标为 unavailable/mono；真实的双单声道可以返回高相关、近零 side 比例，但应区别于缺失数据。静音、极低电平或仅单侧有效时使用有效掩码，不应把除零后的值当测量。

**side 比例高不一定听起来更好或更开阔；反相也可能造成异常大值。**必须同时报告相关度；空间宽度、频谱宽度、混响深度是不同维度。不能据此可靠识别“主唱在前、弦乐在后”。混响/距离估计另设实验功能，验证前不作为确定标签。

## 8. 新增局部律动分析：解决‘中速推进’过于笼统

扩展 `features/rhythm.py`，建议增加：

```python
rhythm_timeline(y, sr, shared_frames, config) -> dict
```

输出候选拍点时间、局部速度与稳定程度、每秒起音数、节拍内起音分布，以及速度变化区间。显示“起音变密但速度近似不变”，不要把起音增加误称加速。

- 拍号需要小节强拍判断。现有 BPM/beat_track 不足以保证识别 4/4 或 3/4；缺少模型或可靠证据时返回未知。
- 处理半速/倍速歧义；保存候选而不是把 80/160 BPM 之一强行当真值。
- 切分感、摇摆感、半拍律动需要专门定义和验证。第一版只给拍点与起音分布，不把自由 rubato 错误标成拍点不稳。
- “重拍更有冲击”可由拍点附近的低频/瞬态变化支持，但不能直接断言真实底鼓力度或轨道音量。

## 9. 可选的人声、旋律、和声与段落模型

### 人声与主旋律

当前 pYIN 在谐波成分上运行，谐波成分包含许多乐器，不能直接当主唱。`vocal.py` 的低置信度估计也不足以可靠区分主唱、和声、说唱。

建议新增可选 `features/source_analysis.py` 或 `models/source_separator.py`，定义统一适配器，先评估 Windows/CPU/GPU 适配及本地性能，再决定具体模型。对选中的歌曲执行深度分析，避免全库自动下载和运行大模型。

有可信人声信号后再输出：人声活动区间、候选主旋律音高、音域、长音比例、发声起音密度、音高滑动。多声部人声仍会干扰单基频估计；没有专用模型时不要输出精确和声层数、男女标签、具体歌手身份或“3 轨和声”。

### 和声

现有三和弦模板已修复，但只支持基本大小三和弦。可扩展七和弦等模板、按节拍平滑序列，并保留 `no_chord/unknown` 和置信差值。需要全曲和声时间线时，另算分段结果，不能把最响窗口的和弦序列铺到整首歌。

### 主歌/副歌/桥段名称

保留 A/B/C 作为独立事实层；功能标签继续标为估计。可新增 `models/structure_labeler.py` 评估专门模型，例如 All-In-One 的边界与功能标签能力。模型版本、类别集合、分数与未支持标签都应暴露；公开标签中没有预副歌时不得承诺它能直接识别预副歌。

相同 chroma 或平均描述向量不代表相同旋律。改进重复分组时，可增加节拍同步序列比较、递归/自相似矩阵与局部对齐；先限制序列长度和候选范围，避免整曲帧级 O(N²) 比较拖垮曲库分析。

## 10. 两仓库之间的接口、缓存与计算策略

### 建议增量接口

继续扩展已有 `/v1/analysis`，不要为每条曲线引入一次独立 HTTP 请求。建议增加：

```json
{
  "capabilities": ["dynamics", "texture", "spatial"],
  "profiles": [],
  "curves": [
    {
      "id": "side_energy_ratio",
      "unit": "ratio",
      "scope": "full_track",
      "time_seconds": [],
      "values": [],
      "valid": [],
      "source": "original_stereo",
      "method_version": "spatial-v1"
    }
  ]
}
```

示例只说明契约，不是当前服务返回值。仍保留旧 `dynamics` 字段和 C++ 单曲线回退路径，使旧客户端/服务可互通。允许各模块时间网格不同；前端只有在时间轴一致或明确重采样后才可逐点比较。

每个模块附带状态 `ready/unavailable/failed/not_requested`、范围、算法版本和来源。数值缺失不能当零，也不能因空间模块不可用就宣布整首分析失败。真实曲长末端使用实际时间桶长度，避免补零制造“结尾骤停”。

### 存储与版本

- 优先复用 `dynamics_json` / 现有结构存储并新增明确的可选模块载荷；必要时增加分析模块表。不要把全部长曲线塞进推荐标量列。
- 算法或字段语义改变时更新版本并提供重算路径；模型、声道处理、配置变更也要进入缓存指纹。
- `AnalyzeTrackAsync` / `AnalyzeLibraryAsync` 当前已有跳过逻辑，扩展后还要检查所请求模块是否完成。仅看到最新 RMS 曲线，不能跳过用户新请求的空间或深度分析。
- 请求深度分析失败时保留基础结果。前端缓存只失效受影响歌曲，切歌后过期回调不能覆盖新歌。
- 推荐 embedding 的字段、维度或缩放器改变时，重建对应模型与 FAISS，并记录版本。

## 11. 实时 FFT 路径可增加什么

离线全曲分析不必搬进音频回调。实时路径适合短时电平、峰值、频段能量、亮度、L/R 相关度等当前状态。

建议新增 `core` 层纯 DSP 类 `RealtimeAudioMetrics`（头文件放入项目现有公开头文件目录），方法接收多声道样本、帧数、采样率，返回一个有时间戳的快照。不同采集块长度时使用固定窗口/滑动缓冲，不能每块独立计算后假装是相同时间尺度。

接线建议：

- `WasapiLoopback.cpp` / `PlayerViewModel.cpp` 保留声道数据，分发给 FFT 绘制和指标处理。
- `SpectrumAnalyzer.cpp` 目前在频谱计算前平均所有声道；空间指标必须在该平均操作之前计算。
- 指标从原始样本或规范化频谱计算，不能由经过 gain/attack/release 的显示柱倒算真实电平。
- 采集回调只处理轻量 DSP 或把有限数据送入有界队列；UI 按较低固定频率更新。禁止回调里执行 HTTP、文件写入或深度模型。
- 分析 FFT 时明确窗函数、归一化和输入长度。显示用 peak-bins 与能量统计用 power-bins 应分开命名。

当前 loopback 采的是默认输出端点的系统混音，其他应用声音、系统音量和设备效果会影响结果。来源应标 `system_loopback`，不能存成原歌曲的永久结构真值或用它替代原文件推荐特征。实现播放流专属采集/解码后才能明确归因于当前曲目。

## 12. 推荐和生成提示词如何利用这些结果

### 推荐

分别比较动态轮廓、纹理、律动、空间与结构，允许选择“音色不同但动态相近”“音色相近但起伏更平稳”。多条强相关指标应成组缩放和加权，避免同一变化通过 RMS、峰值、平均能量等重复计分。

修改引擎 `recommendation/space.py`、`lexicon.py` 和相关配置时，明确新增字段对应的解释、数据覆盖率与可靠性。缺失模块不计入相似度分母；单纯缺数据不应降低歌曲品质分。原始组名 A/B/C 需标准化为首次出现顺序，不能把任意聚类编号当音乐身份。

### 提示词

新增 `features/description.py` 或独立描述层，从结构化数据生成中文/英文制作描述。第一版优先确定性模板，之后如引入语言模型，也要求描述能追溯到证据。

示例输出规则：

- 由局部拍点和起音活动写“速度基本稳定，第二段起音活动增加”。
- 由空间模块写“左右差异增加，中心成分仍占主导”。
- 由重复组和多维曲线写“B 组第三次出现时低频比例和起音率提高”。
- 只有标签可靠时写“副歌”；未知段落用 A/B 或时间区间。
- 不把“明亮、宽、密集、响”合并成空泛的“更有力量”。

这类提示词借鉴听感维度，不承诺通过重现原旋律和标志性片段达到完全一致，也不承诺任何版权结论。

## 13. 建议实施顺序与交付边界

### P0：现有数据的展示和语义修正

- 接入已有多条动态曲线与单位说明。
- 区分 onset 活动和真实起音率；新增实际事件计数。
- 改进多维事件检测，使电平平稳不再屏蔽音色/节奏变化。
- 数据驱动的曲线结构、缺失状态、旧接口回退与缓存检查。

完成后：可以点击一首歌任何时间，比较电平、低频、亮度、起音活动，并清楚说出“什么变了”。

### P1：纹理、空间与动态轮廓

- 共享频谱的纹理模块。
- 原声道保留与空间模块。
- 局部拍点/起音时间线。
- 带维度与证据的 12 种可组合轮廓。
- 推荐组与描述层适配。

完成后：能区分“更亮”“左右差异更大”“低频更多”“重复段逐次加厚”，不依赖曲风或命名乐器。

### P2：有选择的深度分析

- 结构功能模型适配器与人工修正。
- 人声活动、声源分离、主旋律和更丰富和弦时间线。
- 待验证的声源类别、混响、发声方式与复杂纹理模型。

完成后再决定哪些模块适合全库、哪些只按需运行。不要预先承诺正确数出所有乐器/和声轨道，或恢复制作工程中的真实处理链。

## 14. 后续开发的验收要求

建议实现者准备人工听辨样本和可控信号检查，分别验证：

1. 恒定电平但音色变亮：亮度模块有变化，不能硬标响度渐强。
2. BPM 恒定但起音变密：起音率上升，速度无需上升。
3. 双单声道、正常立体声、反相信号、静音：空间指标和 unavailable/valid 状态正确。
4. 低频增多但整体电平变化很小：低频曲线能反映变化，不凭空推断真实 bass 轨道。
5. 同一重复段不同编曲厚度：分组尽量一致，变化在对应维度体现。
6. 单声道原文件和已被预处理合成 mono 的文件：不能输出伪造的空间分析。
7. 末尾补零、文件截断、真正骤停、渐弱尾奏：尽量区分，无法区分则降低分数并注明。
8. 新旧客户端/服务互通、缓存部分完成、模型不可用、后台切歌和取消：基础播放器保持可用。
9. 同一批熟悉歌曲：分别统计边界、分组、轮廓与功能标签误差，不用一个总“准确率”掩盖短板。
10. 性能：记录整曲每模块耗时、峰值内存、缓存体积；当前时间网格保持实用，避免默认加载逐采样点的数据。

本文仅新增开发说明，没有实施上述算法或运行音频验收。
